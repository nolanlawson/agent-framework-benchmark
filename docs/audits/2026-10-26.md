# Audit 2026-10-26

Reviewed the 5-iteration report (published at
https://claude.ai/artifact/NvinBAwEhbMETAGzrRk4uu), its raw data in `runs/20261026-stitched/`
(60 agent runs, 58 measured) and the harness at `c1ba47e`. Reviewer: Claude (Opus 5.5), with
decisions made by Nolan.

The question was the same as last time: what would a skeptical web developer, or a framework
author, object to after reading the report and the code?

Summary: every number in the report recomputes from the raw data. The problem is what the
page-load numbers mean. On this host, Lighthouse's simulated throttling turns most of the LCP
and FCP differences between frameworks into races over Chrome's request priorities (#1, #2).
The cost and time numbers hold up. The objections to them are about interpretation, and Nolan
considers those part of the experiment (#6 to #9). The report hasn't been corrected yet.

### 1. Simulated LCP and FCP mostly measure request priorities

Unthrottled, every app reaches LCP in about 50 ms (`observedLargestContentfulPaint` is 52–92 ms
in the saved reports). Lighthouse's simulation (Lantern) estimates the throttled value from the
requests that finished before that local paint. Two rules in its code decide most of the
results (`bench/node_modules/@paulirish/trace_engine/models/trace/lantern/`):

- **LCP.** `getEstimateFromSimulation` in `metrics/LargestContentfulPaint.js` takes the
  latest end time over the nodes that pass `isNotLowPriorityImageNode`. An LCP image fetched at
  Low priority doesn't count at all. LCP then falls back to the latest script or request that
  finished before the local paint.
- **FCP.** `NetworkNode.hasRenderBlockingPriority` treats any High-priority script that ran
  before the local paint as render-blocking. That includes every `modulepreload`.

Evidence:

- React Router 1 and 2 ship the same `entry.client-W8-pxiZ3.js`. Their Pikachu LCP is 1728 ms
  when Chrome fetched the artwork at Low priority and 2405 ms when it was High.
- Next 2 loads its sprites eagerly. They paint before the JS finishes, so the JS stays out of
  the estimate and home LCP is 951 ms. Next 1, 3, 4 and 5 lazy-load them and get 2035–2187 ms.
- A linear fit over the 290 non-Pikachu page loads explains most of the variance (R² = 0.88):
  LCP ≈ 821 ms + 6.6 ms per KB that finished before the local paint + 458 ms if any request
  to the API origin is included. JS bytes alone give R² = 0.56.
- FCP follows the High-priority JS counted as blocking:

  | Framework | High-priority JS | Simulated FCP (ms) |
  | --- | ---: | ---: |
  | SvelteKit | 36 KB | 1054 |
  | SolidStart | 41 KB | 1053 |
  | Nuxt | 82 KB | 1202 |
  | Angular | 95 KB | 1353 |
  | React Router | 118 KB | 1355 |
  | Next | 0 (~140 KB at Low priority) | ~800 |
  | TanStack Start | 0 (~120 KB at Low priority) | ~800 |

  In a real browser, module scripts don't block the first paint.
- Lantern's timings move in steps of one 150 ms round trip, which is why so many values repeat
  exactly. SvelteKit's FCP is 1054 ms in all 5 iterations.
- Last audit's DevTools-throttled flow ranked the home page differently: Vanilla 1240, Qwik
  1312, everyone else 1810–1910 (2026-10-25 #9).
- The order inside the fast group depends on how you aggregate. With the report's medians,
  Astro leads. With means across iterations, Gracile (1109) is ahead of Astro (1124). Using
  each URL's slowest run, the order is Gracile, SolidStart, Qwik, Hono+htmx, Astro, SvelteKit.
- 22% of page measurements are bimodal (#10). In 27 of those 77, two or three of the five runs
  are in the slow mode, so which mode the median lands in is close to a coin flip.

Is this a problem with LCP and FCP, or with Lighthouse? With Lighthouse's simulated
throttling, mostly. LCP and FCP are fine metrics. Lantern estimates them from a 50 ms local
load, and on a host this fast, small timing races decide what goes into the estimate. Some of
the underlying behavior is real: most server-rendered apps lazy-load the LCP sprite, and
React's automatic image preload is Low priority. But the simulation decides how much each one
counts, and for `fetchpriority=high` it gets the direction wrong (#2). Measuring with real
throttling would give meaningful LCP and FCP: `throttlingMethod: 'devtools'` is one setting in
`measure.mjs`, or the network could be throttled at the packet level.

Decision: open. Nolan is leaning toward leaving LCP and FCP out entirely, or keeping them behind
a big caveat.

### 2. The Pikachu explanation is wrong

The report says the Pikachu page "is limited by the image download" at about 2.1 s. That holds
for 6 frameworks: Astro, Gracile, Hono+htmx, SvelteKit, SolidStart and Nuxt (2103–2110 ms).
React Router (1731) and TanStack Start (1804) are lower for a different reason. React 19's
server renderer adds `<link rel="preload" as="image">` for every `<img>` that isn't lazy, and
Chrome fetches that preload at Low priority. When the priority stays Low, Lantern drops the
image from the estimate (#1). Per-run values follow the recorded priority, for example React
Router 3: [2555, 1729, 1728, 1732, 1729].

Next and Angular preload the artwork at High priority or set `fetchpriority=high`, which is the
recommended practice, and they score worse. That's also why `fetchpriority=high` made no
difference: Lantern splits bandwidth evenly between requests (`simulation/Simulator.js`), so
priority only changes the order requests start in.

Decision: note it in the report.

### 3. Server-side API calls have no latency; browser calls do

The README says so; the report doesn't. An app's server calls the API at localhost speed, and
the browser's calls get Lighthouse's 150 ms round trips. With caches warmed before every run,
server rendering is close to free. The Pikachu page makes 89–164 server-side API calls (every
app fetches moves one at a time), and median TTFB is 2–11 ms. Vanilla's ~100 browser fetches on
the same page are throttled, which puts its Pikachu LCP at ~4.6 s and Vanilla last overall.

Decision: keep the setup. It models an app server in the same datacenter as its API, which is
common. Say so in the report.

### 4. Framework medians mix in agents' architecture choices

The report says some iterations send the whole 1,025-entry index to the browser, and points to
the home-document column. Readers can't tell them apart there, because Qwik's documents are
just as large for another reason (48 cards plus its serialized state). The whole-index
iterations among the measured ones:

| Iteration | Where the index is |
| --- | --- |
| Next 2, 4, 5 | RSC flight payload, ~12 KiB compressed |
| Nuxt 2, 4, 5 | `__NUXT_DATA__`, 22–28 KiB |
| TanStack Start 3 | Dehydrated loader data |
| SolidStart 3 | Seroval script before `<main>`; it runs before the first paint (home FCP 1203 vs 1053) |
| Angular 2 | TransferState, 11 KiB |
| Gracile 5 | A Lit attribute, 10 KiB |

Angular 4 also embeds it (not measured). Gracile 3 fetches it after load and re-renders the
list in the browser. Next 2/4/5, Nuxt 4/5 and Gracile 1/5 also serialize every game's moves
into the Pokémon page.

Eager sprites: Astro 2, Hono+htmx 3, Next 2, Nuxt 5, React Router 5, and Vanilla 1
(`EAGER_CARDS = 120`), which the report leaves out. Astro 2's eager sprites are why its LCP is
1422 ms against about 1020 ms for the other Astro iterations. Only Angular 1 and Vanilla 5
preconnect, and not to the API origin, so every image pays for a new connection (about 450 ms
in the fit in #1).

Decision: name these iterations in the report. They don't sink the experiment. Some frameworks
lead agents into the pit of success and others don't, and that's part of what's measured.

### 5. TBT comes from an uncalibrated CPU

Lighthouse's CPU score for the host (`benchmarkIndex`) is 2519–3091, median about 2900, so the
default 4× slowdown emulates a fast phone. TBT only counts the part of each task over 50 ms, so
5 frameworks show 0. Main-thread time separates them better (simulated, medians in ms):

| Framework | Main thread | JS execution |
| --- | ---: | ---: |
| Astro | 191 | 22 |
| SvelteKit | 343 | 61 |
| React Router | 455 | 207 |
| Nuxt | 561 | 230 |
| Next | 640 | 347 |
| Angular | 726 | 378 |

Apps were measured in framework blocks from 09:08 to 12:34 rather than interleaved. The CPU
score stayed stable over that time, so drift is unlikely to matter.

Decision: add a main-thread time chart. Calibrating the CPU multiplier wasn't discussed.

### 6. A third of the cost comes after the agent's tests already pass

In 49 of 60 runs, the agent's first `npm test` passed 54/54. Afterwards the agents mostly
compared screenshots and adjusted CSS, which nothing scores, plus extra type-checks, unit tests
and repeat test runs. Median share of each run's cost after that first pass: Hono+htmx 26%;
Astro, TanStack Start and Gracile 34%; SvelteKit 38%; Angular 43%; React Router 45%. Measured
up to the first pass, framework medians range from 5.5 to 10.2 min and $1.60 to $3.33.
Angular, Gracile and SvelteKit stay the three most expensive. React Router moves from the third
most expensive to the fourth cheapest.

Decision: keep as is. If agents polish pixels, that's part of the experiment.

### 7. No pairwise difference survives correction for 66 comparisons

The framework effect on cost is clear overall (permutation p < 0.001), but no pair of
frameworks differs after a Holm correction across the 66 pairs. With 5 runs each, an exact
two-sample test can't go below p = 2/252 ≈ 0.008, and the first Holm threshold is
0.05/66 ≈ 0.00076. Neighbors in the cost ranking have p = 0.06 to 0.98. The extremes do
separate: Gracile's cheapest run ($3.92) cost more than Hono+htmx's most expensive ($3.19), and
27 of 66 pairs have p < 0.05 before correction.

Decision: keep. The report shows the spread on purpose, and some frameworks are cheaper or more
expensive than others by more than the spread.

### 8. Model familiarity is part of "framework"

Frameworks newer than the model's knowledge cost more to learn:

- 4 of 5 SvelteKit runs read `kit/migrating-to-sveltekit-3`.
- All 5 Gracile runs cloned its repos or ran `npm pack` to read its source, and hit the "route
  handlers run at build time" gotcha.
- Context per API call averages 130–137k tokens for SvelteKit, Gracile and Angular, against
  about 100k for the others.
- Every Qwik run picked 1.20.x as "latest stable" because v2 is a release candidate.

Tooling doesn't inflate the starting context: MCP tool schemas are deferred, and the first turn
is 17.0k tokens without tooling and 18.0k for Angular. SvelteKit's MCP documentation adds an
estimated $0.20–0.58 per run. The Svelte plugin's skills and subagent were never used.

Decision: note it in the report. It's part of the experiment.

### 9. Vanilla 2's time is inflated by a port conflict in the test runner

The agent left its own debug servers running on ports 3100 and 9100, which `tests/run.mjs` also
uses. The runner doesn't check whether the ports are free, and `waitFor` accepts any response,
so the tests ran against the stale servers and many hit 30 s timeouts. That cost about 6 of
Vanilla 2's 18.6 minutes. `SPEC.md` tells agents the test ports "don't conflict with anything
you're running", which isn't true. Five other runs used those ports without harm.

Decision: note it in the report. It's one iteration and doesn't change the conclusions.

### 10. Smaller wording and labeling errors

Nolan hasn't reviewed these yet, and the report isn't corrected yet.

- "Text in 82 (mostly the client-rendered apps' footer)": 30 of the 82 are footers (Vanilla 25,
  Angular 1 5). The other 52 are the ability page's paragraph in server-rendered apps.
- Bimodal LCP happens "mostly where the LCP element is a lazy-loaded sprite": 35 of the 77
  cases. 30 are text and 12 are eager images.
- "One Lighthouse run (SD)" of 64 ms averages over 6 URLs. Per URL, the SD averages 108 ms and
  reaches 658 ms.
- The summary says Angular's agents "invoked their skills in every run". Angular 4 made no Skill
  tool call; it read both SKILL.md files with `cat`. That's 4 of 5, as the report's own table
  says.
- Next 1 "AGENTS.md ×2" is one read and one deletion.
- "Between batches, the agent's environment didn't change: ... tool versions". The Svelte plugin
  (`b2589f8` → `7b72fc5`) and the Angular skills (`3c880aa` → `4cc56a7`) moved to new commits at
  iteration 4.
- The eager-sprite list leaves out Vanilla 1 (#4).
- "Every app renders its pages on the server except Vanilla and Angular 1". Gracile 3 renders on
  the server but then re-renders the list in the browser.
- "JavaScript transferred" leaves out inline scripts. These are uncompressed medians per page:
  Next ~61 KB (RSC payload, 154 KB on Next 2's move page), React Router 15 KB, SolidStart 11 KB,
  TanStack Start 11 KB, SvelteKit 10 KB. Astro's "0 KiB" hides 0.8–1.5 KB of inline module
  script.
- Gracile 2 and 4 send no Lit to the browser at all: server templates plus 1.5–3.4 KB of plain
  custom elements. Gracile 3 uses lit-html's `render()` without hydration. Only Gracile 1 and 5
  hydrate LitElement components.
- Qwik 3 has no `trailingSlash` setting, so 4 of its 6 URLs go through a 301. Lighthouse
  estimates 750 ms lost; the simulated metrics don't include it. Its warm-up also only hits the
  301, so its server cache isn't warmed (negligible with a zero-latency API).
- Next 1/2 and React Router 1/3/4 compress their own responses, which the spec asks apps not to
  do. Caddy doesn't re-encode them, so those apps get gzip or brotli instead of zstd. The byte
  difference is small.
- "60/60 agent runs passed". True for the tests, but Angular 3 and 4 return HTTP 400 behind the
  reverse proxy the spec describes (hard-coded `allowedHosts`). A skeptic will count those as
  failures.
- Lines of code include template boilerplate: 167–337 lines of Qwik config (Qwik 3 and 5
  include a 71-line `eslint.config.js` and a 95-line `vite.config.ts`) and 112–159 lines of
  Angular server scaffold.
- The report doesn't link to the code or the raw data, so framework authors can't check it
  (2026-10-25 #19).

## Checked and fine

- **Numbers.** Totals ($212.73, 10.99 h), every median and min–max in the agent and page-load
  tables, the per-page tables, and the 3-versus-5-iteration table all recompute from the
  transcripts and `results.json`. So do the shares of variance (the intraclass correlation:
  cost 0.54, time 0.29, turns 0.35, tokens 0.49, LCP 0.88, TBT 0.92, FCP 0.98) and the
  permutation p-values. CLS is 0.111 on every page of every Vanilla iteration and Angular 1,
  and 0 elsewhere.
- **Agent setup.** All 60 runs used claude-opus-5-5 at effort high with Claude Code 2.1.310.
  The only other model is claude-haiku-5-5, in TanStack Start 4 ($0.003, summarizing two
  WebFetch calls). Between `4247b96` and `c1ba47e`, `template/` and the agent side of
  `bench/container/` changed only in the Svelte plugin ID and the React Router skill.
- **Time.** No API errors, retries or rate limiting. All stderr logs are empty. No hung tool
  calls. Output tokens per second show no drift across the batches or the fixed run order.
- **Tooling counts.** Apart from the two errors in #10, every MCP, Skill and skill-file count
  matches the transcripts. No agent used WebSearch or a subagent. Some agents read docs bundled
  in `node_modules` (Next 3, 4 and 5, and all 5 React Router runs) or fetched them from the shell (TanStack 2,
  SolidStart 1, every Gracile run); the report's counts leave these out.
- **Integrity.** All 60 final test runs passed 54/54, and `retries` is 0. No agent changed
  tests, data, the API or the design files. No app hard-codes data, reads `data/`, prerenders
  data pages, warms data at startup or uses a CSS framework. Every app uses the real artwork
  and sprite URLs from the API origin.

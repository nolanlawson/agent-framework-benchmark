## Numbers

### 1. JS execution time leaves out scripts under 50 ms

The column uses Lighthouse's `bootup-time` audit. That audit only lists script URLs with at
least 50 ms of CPU time after the 4× multiplier, about 12.5 ms real
(`bench/node_modules/lighthouse/core/audits/bootup-time.js`, the threshold near line 131).
Frameworks that split their JS into many small chunks lose most of it.

Home page, script evaluation plus parse/compile from the same saved report's
`mainthread-work-breakdown`, against the report's value:

| Framework | Full script time (ms) | Report (ms) | What's dropped |
| --- | ---: | ---: | --- |
| SvelteKit | 109 | 62 | All 13 small chunks |
| Qwik | 123 | 68 | 20 of 22 scripts |
| Hono + htmx | 56 | 27 | htmx.js |
| Nuxt | 272 | 240 | |
| Next.js | 407 | 372 | |

Astro, Vanilla, React Router, TanStack Start and Angular lose 3–5 ms. With the full count,
Vanilla (75 ms) runs less script than SvelteKit or Qwik, which reverses the report's order.

Decision: remove the metric from the report. If it comes back, use `scriptEvaluation` +
`scriptParseCompile` from `mainthread-work-breakdown`, which the saved reports already have.

### 2. First `npm test` passed in 53 of 60 runs, not 49

In 5 runs the first Bash command containing `npm test` began with `pkill -f "api/server.mjs"`.
The pattern matches the shell's own command line, so the shell killed itself: `Exit code 144`
within about 25 ms, and the tests never ran. The runs are next-1, qwik-1, tanstack-start-2,
react-router-2 and sveltekit-2.

Counting the first test run that actually ran, 7 runs failed it: nuxt-2, vanilla-2, vanilla-3,
next-1 (49 of 54), tanstack-start-5, sveltekit-1 and angular-1. That's 53 of 60.

The "cost up to first pass" figures depend on a choice the report doesn't state. In stream-json,
each assistant message's input, cache-write and cache-read counts are exact, but its
`output_tokens` is only the value at the start of streaming. Angular-1's messages sum to 814
output tokens against 76,572 in the result event. The report's $1.60–$3.33 reproduces only if
each run's output tokens are spread evenly over its requests. Weighting output by what each
request produced gives $1.86–$3.54. These hold under every method tried: "about a third after
first pass" (31–36%), the 5.5–10.2 min time range, and Angular, Gracile and SvelteKit staying
the three most expensive.

Decision: correct the report. When the first-pass numbers are recomputed, skip the self-killed
runs and say how output tokens were split.

### 3. The React Router Pikachu example compares a single run with a median

The report says React Router 1 measured 1,728 ms with the artwork at Low priority, and
iterations 2 and 3 measured 2,405 and 2,555 ms at High. The priorities in the saved reports are
right. But 2,555 ms is React Router 3's first run only. Its five runs are 2555, 1729, 1728, 1732
and 1729, so its median is 1,729, and 2,555 appears in no table.

"With the same code" is loose too. The artwork markup is equivalent, and all three ship React
Router's identical `entry.client-W8-pxiZ3.js` (which 2026-10-26 #1 cited). The app's own chunks
differ (`pokemon-*.js`, `root-*.js`, `format-*.js`). A cleaner example is React Router 3 against
itself: 2,555 ms in the run where the artwork was High, about 1,729 in the others.

Decision: not used in the takeaways.

### 4. Wrong or incomplete statements in "Patterns in the code"

- **Preconnect.** The report says Angular 1 and Vanilla 5 preconnect, "not to the API origin
  that serves the images". Both preconnect to `API_BASE_URL`, which is
  `https://api.localhost:8444`, the image origin (Angular 1 `src/index.html:9`, filled in by
  `server/server.mjs:42`; Vanilla 5 `server.mjs:29`). The preconnect is `crossorigin`, so it
  helps their `fetch()` calls but not the `<img>` requests, which need a credentialed
  connection.
- **Eager sprites.** The list leaves out three iterations. React Router 2 sets
  `loading={i < 12 ? "eager" : "lazy"}` (`app/components/PokemonCards.tsx:18`). Angular 2 and 5
  give the first 6 cards `NgOptimizedImage` `priority` (`[priorityCount]="6"`), which adds
  `fetchpriority="high"` and a preload link. Their home LCP element is that sprite. The table's
  "Sprites" column misses them because of its 60 KiB threshold.
- **Gracile 3.** It doesn't re-render the list on load. `src/routes/(home).client.ts:88-95` only
  calls `render()` when the controls differ from the URL. It does fetch `/api/species-index`,
  the full 1,025-entry index (16 KiB), on every home-page load, so it belongs in the whole-list
  table. The client-rendered apps also fetch the full species list
  (`pokemon-species?limit=100000`, 9 KiB), which the table doesn't mention.
- **React's artwork preload.** It isn't specific to React Router and TanStack Start. React's
  server renderer preloads any `<img>` that isn't `loading="lazy"`, Next.js included: in all 5
  Next.js iterations the artwork is the second request, before the CSS. Chrome fetched it at
  High in all 5 Next.js runs, at Low in 3 of 5 React Router and 4 of 5 TanStack Start runs.
  Angular 2 and 5 preload it too, through `NgOptimizedImage`.
- **Compression.** Next 1 and 2 kept Next's default `compress`; 3–5 turned it off. React Router
  1, 3 and 4 use `react-router-serve`, which adds `compression()`
  (`@react-router/serve/dist/cli.js:114`). These are framework defaults, not choices to go
  against the spec.
- **Angular scaffolding.** "112–159 lines of Angular server setup" includes Angular 1's
  hand-written 129-line static server and the `/_data` endpoints Angular 2 and 5 added. That's
  more than scaffolding. The Qwik figure (167–337 lines) is right.
- **Payload sizes.** Nuxt 2, 4 and 5's whole compressed home document is 24, 30 and 23 KiB
  against 5–6 KiB for Nuxt 1 and 3, so "`__NUXT_DATA__`, 22–28 KiB" can't be compressed. Say
  which. Next's extra is about 10 KiB (report: 12) and Gracile 5's about 12 KiB (report: 10).
- **Not mentioned.** Prefetching adds requests to the measured load. Next 1, 2 and 4 make
  11–12 `?_rsc` fetches on the home page, Next 3 and 5 make 2, and Qwik makes 7
  `q-data.json` fetches plus `bundle-graph.json`.

Decision: not in the takeaways. Fixing the page is optional.

### 5. Smaller number and label fixes

- "A framework's median LCP moves by at most 599 ms between those pages and the home page." The
  largest move against the home page is 525 ms (TanStack Start, Static). 599 ms is Static
  against Fire type.
- "89–164 API calls" on the Pikachu page can't be checked from saved data, since nothing records
  server-side calls. It also doesn't apply to Vanilla or Angular 1, which serve an empty shell.
- "Unthrottled, every page reached LCP in 27–329 ms" comes from first runs only, and the 27 ms
  is Vanilla's footer, not content.
- Tokens are labelled "cache reads + uncached input + output". `report.mjs` counts cache writes
  as uncached input, and the page doesn't say so. Cache writes are about 2% of the total.
- "$0.69 (19%)" and "$3.48 without lookups" are medians of per-run values, so they don't match
  0.69 / 4.28 (16%) or 4.28 − 0.69 (3.59). Readers will do that subtraction. Same for Gracile
  and Angular.
- SvelteKit "along with pages on environment variables, adapter-node and navigation": the
  environment-variable pages were fetched in 5 of 5 runs, adapter-node and `$app/navigation`
  only in runs 1 and 3.
- "Every run used the same model": tanstack-start-4 also used `claude-haiku-5-5` for $0.003 to
  summarize two WebFetch results (2026-10-26 noted this too). It's in `total_cost_usd`.

Decision: low priority. Fix if convenient.

## Claims (context, not repeated in the takeaways)

### 6. "The differences between frameworks are small" isn't tested

The summary says load-time differences are small and that this setup can't measure them. Both
can't be true. The evidence offered, a 62 ms median unthrottled LCP, is a page load on the same
machine with no network, so it says nothing about a phone. No real-throttled measurement was
made, and Lantern still models bandwidth: its pessimistic LCP estimate counts every request
before the paint. A framework author could object from either side. The supportable statement
is "this setup can't separate the frameworks' load times."

### 7. "Request priorities, not the frameworks" ignores that frameworks set the priorities

The Lantern rules check out in source (`@paulirish/trace_engine/.../lantern`). LCP ignores Low
and VeryLow images. FCP treats any High-priority script that finished before the paint as
blocking, and module chunks never emit the event Lantern uses to rule a script out, so
`modulepreload` counts. SvelteKit has 13 High-priority `modulepreload` scripts and FCP of about
1,055 ms in all 25 runs. TanStack Start and Next.js load scripts at Low.

The frameworks choose those priorities: SvelteKit emits `modulepreload`, React preloads
images, and TanStack Start's scripts load at Low. "Framework resource hints, as Lantern scores them" is
fairer than "not the frameworks."

### 8. Main-thread time comes from one run, the cold first run on the home page

The report calls main-thread time "the clearest real difference" and "reliable". It comes from
the one saved report per URL, the first of 5 runs, while every other metric is a median.
`results.json` stores no per-run main-thread or bootup values.

`measure.mjs` runs page by page, so home run 1 is the first Lighthouse run after the app starts.
It looks cold. Compared with the median of runs 2–5, its server response time is higher in 50 of
58 iterations (by about 2 ms), and its simulated LCP and FCP are higher in 46 and 47 of 58. Its
TBT is about 1.15× runs 2–5 on Home and Filtered, about 0.97× on the other pages. Single runs are
noisy too. TBT over 5 runs spans 137–360 ms for Nuxt 5 on Thunderbolt and 649–998 ms for Angular
1 on Pikachu.

"Following how much JavaScript each framework runs" is loose. Rank correlation with main-thread
time is 0.84 for JS bytes. But Lighthouse's "Other" category is 25–63% of main-thread time and
the largest category for 7 of 12 frameworks (Vanilla: Other 219 ms, script 72; Qwik: Other
225, script 118). "Other" includes image decoding: the eager-sprite iterations show 779–1,120 ms
of it on Thunderbolt. The 4× multiplier is applied under simulated throttling
(`mainthread-work-breakdown.js:103`), as the report says.

A fix would add main-thread and script time to `summarizeLhr` and take the median like the other
metrics, then re-run measurement only, about 3.5 hours. That adds code, so it's only worth it if
main-thread time goes into the takeaways.

### 9. The Angular exclusion blames Angular for a gap in the spec

The summary says two Angular apps "failed behind the reverse proxy the spec describes". SPEC.md
says a reverse proxy will sit in front and handle HTTPS, HTTP/2 and compression. It never names
the host or says the Host header will differ, and the tests only use localhost.

`@angular/ssr` 22.2.4 rejects every host when the list is empty (`ssr.mjs:1459`), so each
server-rendering Angular agent had to choose a list:

| Iteration | allowedHosts | Measured |
| --- | --- | --- |
| Angular 2 | `['*']` in `server.ts` | Yes |
| Angular 3 | `['localhost', '127.0.0.1', '[::1]']` in `server.ts` | No, HTTP 400 |
| Angular 4 | A list in `angular.json`, none in code | No, HTTP 400 |
| Angular 5 | `['*']` unless `NG_ALLOWED_HOSTS` is set | Yes |

So the measured apps are the two that turned off Angular's SSRF protection. The excluded ones
followed Angular's advice to allow only known hosts. Angular's n=3 is then two server-rendered
apps and the one client-rendered app, Angular 1.

Angular 3's comment says to set `NG_ALLOWED_HOSTS`, which Angular ignores when the list is set
in code (`node.mjs:322`: `options?.allowedHosts ?? getAllowedHostsFromEnv()`). Angular 4 calls
`new AngularNodeAppEngine()` with no options, so `NG_ALLOWED_HOSTS=app.localhost` would have
let it be measured.

Fairer wording: "The spec doesn't name the proxy's host, and the tests use localhost. Angular 3
and 4 allowed only localhost and returned HTTP 400 behind the proxy. Angular 2 and 5 allowed any
host."

### 10. "Without lookups, SvelteKit would be $3.48" is a counterfactual

Subtracting the lookup cost assumes the agent would have done as well without reading the docs.
It might have made more mistakes instead. "Lookups account for about $0.69 per run" says what
was measured. The same applies to Gracile's "$3.88, still second". See also #5 for why the
numbers don't subtract.

### 11. The addendum calls the review independent and says every number recomputed

The earlier review was the same model, and this one found wrong numbers (#1, #2, #3). "A
second agent reviewed..." is accurate. "Independent" and "every number recomputed correctly"
will draw fire.

## Methodology (open)

### 12. Measurement order is blocked by framework

`measureAll` runs the iterations in directory order, so the apps were measured alphabetically
by framework from 09:08 to 12:34 UTC. Framework and time slot are confounded. The host didn't
drift: Lighthouse's `benchmarkIndex` has a per-app median of 2,807–2,961 throughout, and no
trend. Saying so in the report heads off the question. If measurement is ever re-run, shuffling
the directory list is a one-line change.

### 13. The report still doesn't link to the code or the raw data

This was 2026-10-25 #19 and 2026-10-26 #10. The report names `docs/audits/2026-10-26.md` "in
the benchmark repository" without a link. Framework authors will want to look at their own
framework's apps.

### 14. The takeaways speak for one model

Every run used Claude Opus 5.5 at effort high with one prompt. Cost differences partly reflect
what this model knows (SvelteKit 3, Gracile). Takeaways should say "for Claude Opus 5.5" rather
than suggest some frameworks are harder for coding agents in general.

# Audit 2026-10-25

Reviewed the hand-stitched report for run `20261025-143712` (published as a claude.ai
artifact), its raw data in `runs/20261025-143712/`, and the harness at `87b49c1`. Line
numbers refer to that commit. Reviewer: Claude (Opus 5.5), with decisions made by Nolan.

The question was what a skeptical web developer, or a framework author, would object to
after reading the report and the code: wrong numbers, misleading presentation, and weak
methodology.

Summary: the cost, time and token numbers are right, and so are almost all of the
Lighthouse values. One interaction metric is broken (#1). Several page-load numbers don't
mean what a reader would assume (#2, #3, #10). Two columns are noise (#4, #5) and one isn't
reproducible (#6). Most fixes remove code. The biggest change is procedural: a fresh run
with 3 iterations per framework (#14).

Nothing is fixed yet. The original implementer is picking this up.

### 1. "Change game" latency times the URL change, not the result

The wait in `bench/measure.mjs:209` needs `game=sword-shield` in the URL, an h1 of
`Charizard`, and *any* table. The Base stats table always satisfies the last part, so the
metric is "time until the URL changes". Apps that update the URL before fetching look
20× faster than apps that update it after the response arrives.

| App | Reported | Last request of the step ends (flow run 0) |
| --- | ---: | ---: |
| Angular | 107 ms | ~1009 ms |
| Astro | 24 ms | ~594 ms |
| Nuxt | 39 ms | ~589 ms |
| TanStack Start | 37 ms | ~585 ms |
| Vanilla | 36 ms | ~1006 ms |

Gracile's 59 ms is real (all games are in the page; the step makes no request). Hono's 861 ms
is an honest round trip: htmx pushes the URL only after the response.

Decision: remove the latency metric. **Keep a correct wait anyway**: the flow still needs it
to sequence the steps. If #12's per-step TBT and CLS are reported, the timespan has to cover
the real work. Right now the step ends about 1 s after the URL changes (the `setTimeout` at
`measure.mjs:139`), and Angular's and Vanilla's data lands at about 1 s, so their rendering
may fall outside the step. Waiting for a move row that exists only in the Sword/Shield tables
costs about the same code as the current check.

### 2. Angular and Vanilla LCP measures the footer in an empty shell

On `/`, `/?type=…`, `/moves/thunderbolt`, `/abilities/static` and `/types/fire`, the
`lcp-breakdown-insight` element is the footer's "Data from PokéAPI…" paragraph
(412×42 px). Both apps render in the browser. The footer paints in the empty shell before any
data arrives, and the 96 px cards that come later are smaller, so they never replace it.
Vanilla's home LCP of 760 ms (equal to its FCP, the best in the table) is time to an empty
page. The footer later moving down to y≈5550 is also the 0.111 CLS on all 6 URLs for both
apps. Only `/pokemon/pikachu` measures real content for them (Angular 4956 ms).

Is there a way around it? Not inside Lighthouse. LCP behaves as specified: it reports the
largest element painted so far, and later, smaller elements never replace an earlier, larger
one. The usual workaround is a custom "content visible" mark (for example, time until the
first card renders), which means new code. Decision: explain it in the report, and mark the
affected cells.

### 3. Simulated LCP is bimodal; the median picks the LCP winner

`/moves/thunderbolt` comes out at either ~850 or ~1660 ms for Hono, Astro and Gracile. Hono
got the fast mode in 3 of 5 runs (median 854); Astro and Gracile in 1 of 5 (median 1660).
With 1660 for Hono, its mean would be ~1218 and Astro (1153) would lead the summary. Other
split URLs: Next.js pikachu [1353, 1353, 2105, 2554, 2559] and ability; React Router home,
pikachu and ability; SvelteKit home; TanStack Start on 5 of 6 URLs; Vanilla move and type.

This comes from Lighthouse's simulation, not from LCP itself. The flow's DevTools-throttled
runs were tight: spreads across 3 runs were mostly under 25 ms, with no second mode (the
widest was Qwik's Change game, 610/613/772). More runs won't remove the second mode. Options, cheapest first:

- Say so in the report, and give the per-URL range next to the median.
- Switch page loads to `throttlingMethod: 'devtools'` (one setting in `measure.mjs`). That
  is stable and matches the flow. It is also what #9 is about, so the two would be decided
  together.

Decision: explain in the report. The DevTools option is open.

A related detail: medians are taken per metric (`measure.mjs:96`), so LCP, TBT and score
at one URL can come from different runs. That changes means by up to ~75 ms (Next.js
1890 vs ~1814 using the median run). It's fine, but the report should say "median per metric".

### 4. Visual match: a blank page scores 0.901

A white page scored with the same pixelmatch settings against the 18 reference screenshots
averages 0.901 (`types-mobile` 0.599, everything else 0.84–0.96). The reported range,
0.930–0.991, uses the top tenth of the scale. React Router (0.930) is barely above blank.

Decision: remove it. The accessibility-tree tests already check the content.

### 5. Deps column is mislabeled and doesn't compare frameworks

The report says "runtime dependencies in package.json". `bench/report.mjs:79` adds
`devDependencies`. Only Astro and Nuxt match either reading. Qwik and SvelteKit list
everything as dev dependencies by convention, so neither count compares frameworks.

Decision: remove it.

### 6. SLOC numbers aren't reproducible from the run data

The report's SLOC values reproduce exactly with cloc 1.98 plus hand filters. Those filters:
exclude JSON, Markdown, INI and SVG; exclude `tokens.css` and `routeTree.gen.ts`; count
`.astro` and `.svelte` with Vue rules. But `measure.mjs:279-306` counts raw lines, including
JSON, blanks and comments: Angular is 2644 in `results.json`, 2005 in the report. The
report's footer ("Generated from summary.json, */measure/results.json") is wrong for this
column. Other problems:

- The chart subtitle says config is excluded, but `vite.config.ts` and `astro.config.mjs`
  are counted.
- Angular's count includes the agent's `*.spec.ts` unit tests.

Decision: make it scripted and simpler. For example, count non-blank lines in
`codeStats()` and change the filters:

- Count: files from `git ls-files` with source extensions.
- Exclude: lockfiles, JSON, `tokens.css`, generated files and test files.
- Leave comments in, which avoids cloc's per-language comment rules for `.svelte` and `.astro`.

That replaces the current counter rather than adding one. Describe the rule in the report
exactly as the code applies it.

### 7. Smaller label and wording errors in the report

- **React Router tooling.** "none (skill added by create-react-router)" is wrong. The agent
  wrote `package.json` by hand and the repo has no skill. Fix: "none".
- **"Uncached input (k)".** About 99.9% of it is cache writes (Angular: 144 plain input
  tokens, 193,017 cache writes). `report.md` explains this; the published report doesn't.
  Fix: say so in the table note.
- **Measurement commit.** `config.json` records `harnessCommit` for the agent runs only.
  `--measure-only` measures with whatever is checked out and records image IDs
  (`measureOnlyImages`) but not the commit. So the report's "measurements: `87b49c1`" can't
  be traced to the run folder; it came from memory. Its commit time (20:18:48Z) does
  precede the first `measuredAt` (20:20:17Z). Accepted as is.
- **"Measurement noise" caveat** (earlier passes agreed within 0.3 points). The earlier
  passes' data was overwritten, so readers have to take it on trust. Accepted.
- **Other wording:**
  - "Lowest single URL was 62" is a per-URL median; one Angular pikachu run scored 57.
  - TanStack Start's performance is exactly 99.50, so "9 of 12 round to 100" depends on
    rounding half up.
  - "Chrome trusts the proxy's certificate authority" is really
    `--ignore-certificate-errors-spki-list` pinning. Same effect, slightly different words.

### 8. Angular was built client-only (`--ssr=false`)

The agent ran `ng new … --ssr=false` and gave no reason, while the Angular CLI MCP
(`get_best_practices`) and the `angular-new-app` skill were installed and used. The result
is a client-rendered app compared with server-rendered ones. On the Pokémon page the
browser makes ~100 API requests, against 0 for the server-rendered apps, whose servers make
the same calls at localhost speed.

Decision: keep it. Telling the agent "use Angular" and getting a client-only app is a data
point, especially with Angular's own tooling installed. The spec deliberately doesn't steer
toward performance. Call it out in the report, along with what the Angular tooling said, if
the transcript shows it.

### 9. Lighthouse's simulated throttling shapes the page-load numbers

Unthrottled, every app reached FCP and LCP in under 200 ms, except Angular on pikachu
(326 ms). Lantern's simulation then decides the numbers:

- It drops Low-priority images from LCP. Every server-rendered app puts `loading="lazy"` on
  the first card sprite, which is the LCP element, so list-page LCP mostly reflects how
  much JavaScript is requested first.
- It counts a script toward FCP only if it happened to run before the local first paint.
  That's why React Router (modulepreloaded scripts) has an FCP of 1355 and TanStack Start
  (scripts at the end of body) has 800.

The flow's DevTools-throttled home load ranks the apps differently: Vanilla 1240 and Qwik
1312, everyone else 1810–1910.

Decision: explain it in the report; Lighthouse's defaults stay. See #3 for the DevTools
alternative.

### 10. Pikachu LCP is one unoptimized image's download time

On every app the LCP element is the official artwork: a 118 KB PNG from the API's origin.
No app preconnects, preloads or optimizes it, and only Angular sets `fetchpriority`. The
~2105 ms cluster is that download, not the framework. Angular's 4956 ms is its
client-side waterfall plus ~100 move requests competing for bandwidth.

Decision open: keep the URL with a caveat, or drop it.

### 11. Interaction latencies measure debounce, round trips and harness overhead

- **Search:** mostly the debounce each agent picked (150, 200 or 250 ms) plus one throttled
  round trip (~562 ms), or none for the two apps that filter in the browser (Angular 252,
  Vanilla 176).
- **Sort moves (78–116 ms):** mostly CDP and polling overhead. INP for the same click is
  10–84 ms.
- **Open Pokémon:** a mix of round trips and chunk waterfalls:
  - Qwik: 4 levels of lazy chunks.
  - Next.js: a client chunk found only in the RSC payload.
  - React Router: a route chunk, then a `Section` chunk.
  - Angular: 5 sequential round trips.

  These are real effects, but the wait (`measure.mjs:176`) only needs the h1 and "Base
  stats", not the moves table.
- **Change game:** see #1.

Decision: remove Search, Sort and Change game latency. Undecided: whether Open Pokémon
stays. If it does, its wait should include the moves table.

### 12. Per-step TBT and CLS from the flow are measured but not reported

`results.json` already has them under `flow.steps`. Notable values:

- **TBT:**
  - Angular Open Pokémon 594 ms
  - Qwik Open Pokémon 286 ms and Change game 236 ms
  - Hono Change game 214 ms
  - Next.js Load home 122 ms
- **CLS:**
  - The Search step shifts layout by ~0.22–0.23 in Next.js, Nuxt, React Router, SvelteKit
    and TanStack Start.
  - Sort moves shifts by 0.23 in Qwik, ~0.16 in Next.js and React Router, and 0.055 in Nuxt.

Decision: add them to the report. Check first whether those shifts count as following user
input (Lighthouse excludes shifts within 500 ms of input). See #1 about step boundaries.

### 13. Server caches are cold for some runs

The agents' API caches live 30 s (Qwik, TanStack Start), 60 s (most) or 5 min (Gracile;
Angular's browser cache is also 5 min but doesn't survive a fresh Chrome). The warm-up
(`measure.mjs:316-319`) runs once per app, before ~6 URLs × 5 Lighthouse runs. So:

- Some runs are cold. For example, run 0 on pikachu for SolidStart and SvelteKit has a TTFB
  of ~115 ms, against ~5 ms warm.
- Gracile (5 min) is the only one still warm at run 0.
- The saved Lighthouse JSON is run 0 (`measure.mjs:91`), so anyone opening it sees the
  cold run.
- The flow's pages (Charizard, the search results) aren't warmed at all.

Decision: fix. A warm-up right before each URL's runs keeps any TTL under a minute warm.
For example, move the `fetch` into `runLighthouse()`'s loop, or throw away one Lighthouse
run per URL, which also warms Node's JIT. Warm the flow's URLs the same way.

### 14. One iteration per framework

The cost ranking ($2.35–$4.97) and every per-app performance number are single samples, and
the agents' choices drive the results:

- lazy-loading the LCP sprite
- prefetch settings
- debounce values
- how far the server fans out to the API
- `--ssr=false`

SvelteKit's 8.53M tokens are a good example. Its tests passed 53/54 on the first try. The
tokens came from ~30 screenshot reads during visual polishing, which stay in context for
every later turn, plus two `pkill` mishaps that killed the agent's own shell.

Decision: a fresh run with 3 iterations per framework, reporting the median. Point out the
SvelteKit case in the report as an example of why single runs mislead.

### 15. Qwik 1.x rather than Qwik 2

The agent checked `npm view @qwik.dev/core dist-tags`, saw `2.0.0-rc.3` and chose v1. Qwik
maintainers may say v2's preloader fixes the chunk waterfall seen in Open Pokémon. Fine as
is: the prompt says "latest stable".

### 16. Next.js gzips its own responses, so no zstd from Caddy

Caddy doesn't re-encode responses that already have `Content-Encoding`. This makes Next's
byte counts slightly worse than they'd be with zstd. Minor; won't fix.

### 17. Build times may come from a warm build cache

`repo.tar.gz` excludes only `node_modules`, `data` and `test-results`, so the agent's
`.next/cache` and `.angular/cache` reach the measure container. Won't fix; build time may
not be worth reporting at all.

### 18. agent-browser isn't mentioned in the report

Every agent had the agent-browser 0.39.2 CLI, which ships its own skills, and agents used it
through Bash. Decision: add it to the methodology.

### 19. `runs/` is gitignored, so reviewers can't see raw data

Framework authors will want the transcripts, `results.json` files and Lighthouse reports.
Nolan will find a way to share them.
